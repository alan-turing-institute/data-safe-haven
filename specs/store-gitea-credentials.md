# Plan: store generated Gitea credentials in Azure Key Vault

No tracked GitHub issue found for this (searched both the fork and
`alan-turing-institute/data-safe-haven` for "gitea password"/"gitea
credential"/"key vault gitea" — nothing matched); this plan is written
directly from the SRE team's request.

## 1. Background

Each SRE deployment provisions two Gitea instances via
`data_safe_haven/infrastructure/programs/sre/`:

- `SREGiteaServerComponent` (`gitea_server.py`) — the workspace-facing
  instance (`dns_record_name = "gitea"`).
- `SREGiteaMirrorManagerComponent` (`gitea_mirror_manager.py`) — a
  container group with its own internet-facing Gitea instance
  (`dns_record_name = "giteamirror"`) plus the `mirrormanager` sidecar.

Both instances are configured by a `configure.mustache.sh` init script
(`data_safe_haven/resources/gitea/gitea/configure.mustache.sh` and the
`gitea/gitea-mirror` variant) that creates two well-known, constant
usernames on container start:

1. **An admin user** (`dshadmin`), created with Gitea's own
   `--random-password --random-password-length 20` flag
   (`configure.mustache.sh:6`). Gitea generates this password itself and
   prints it to stdout; only stderr is redirected to `/dev/null`. Pulumi
   never sees this value — it exists only transiently in the container's
   stdout, which flows into Log Analytics as diagnostic logs. There is no
   queryable secret store for it today: recovering it means grepping logs,
   and any redeploy that replaces the container (`gitea_server.py:389`,
   `replace_on_changes=["containers"]`) silently regenerates and re-loses a
   new one.
2. **A non-admin service user** (`workspaceuser` on the `gitea` instance,
   `mirroruser` on `giteamirror`), whose password *is* already a Pulumi
   resource — `pulumi_random.RandomPassword` created locally inside each
   component (`gitea_server.py:135-139`, `gitea_mirror_manager.py:105-112`)
   — but is only ever injected into containers as an Azure Container
   Instance "secure" environment variable
   (`WORKSPACE_SERVER_PASSWORD`/`MIRROR_SERVER_PASSWORD`). ACI secure env
   vars are masked in the portal/ARM but are not stored anywhere
   retrievable after the fact either — same practical problem as the admin
   password, just generated by Pulumi instead of by Gitea.

Elsewhere in the SRE Pulumi program, generated passwords already follow a
consistent, retrievable pattern. `SREDataComponent`
(`data_safe_haven/infrastructure/programs/sre/data.py`) creates a
per-SRE Key Vault (`key_vault = keyvault.Vault(f"{self._name}_kv_secrets",
..., vault_name=get_key_vault_name(stack_name)[:24], ...)`,
`data.py:134-221`) with full access granted to the SHM admin AAD group and
read-only access to a "key vault reader" managed identity. Six existing
secrets (nexus admin, nexus database admin, shared database admin, user
database admin, workspace admin, database service admin — `data.py`
~lines 246-382) follow the same shape:

```python
password_nexus_admin = pulumi_random.RandomPassword(
    f"{self._name}_password_nexus_admin", length=20, special=True,
    opts=ResourceOptions.merge(child_opts, ResourceOptions(parent=key_vault)),
)
keyvault.Secret(
    f"{self._name}_kvs_password_nexus_admin",
    properties=keyvault.SecretPropertiesArgs(value=password_nexus_admin.result),
    resource_group_name=props.resource_group_name,
    secret_name="password-nexus-admin",
    vault_name=key_vault.name,
    opts=ResourceOptions.merge(child_opts, ResourceOptions(parent=password_nexus_admin)),
    tags=child_tags,
)
```

For secrets that need to be read back outside Pulumi, only the *secret
name* (never the value) is exported (`data.py:820-826`,
`pulumi.export("data", data.exports)` in `declarative_sre.py:525`), and
`AzureSdk.get_keyvault_secret(key_vault_name, secret_name)`
(`data_safe_haven/external/api/azure_sdk.py:853-876`) is the existing
helper that reads it — used today by
`data_safe_haven/provisioning/sre_provisioning_manager.py:33-63` for the
database admin passwords. Because the SHM admin AAD group already has
`get`/`list` rights on the Key Vault, once a secret exists there an SRE
admin can already read it directly via the Azure Portal or `az keyvault
secret show`, without any new code.

This plan brings the four Gitea passwords (two admin, two service-user) in
line with that existing pattern, so they survive redeploys and are
recoverable the same way the other generated credentials already are.

## 2. Goal

Store all four generated Gitea passwords in the SRE's existing Key Vault:

- `password-gitea-server-admin` — `gitea_server.py`'s `dshadmin` admin user.
- `password-gitea-workspace-user` — `gitea_server.py`'s `workspaceuser`.
- `password-gitea-mirror-server-admin` — `gitea_mirror_manager.py`'s
  `dshadmin` admin user (on `giteamirror`).
- `password-gitea-mirror-user` — `gitea_mirror_manager.py`'s
  `mirroruser`.

No behaviour change for Gitea itself or for `mirrormanager`'s
authentication flow — this is additive secret storage, not a rework of
how the containers use these passwords.

## 3. Design

### 3.1 Where secret creation should live

Two existing patterns compete here:

- **Centralized** (used by the 6 secrets above): `RandomPassword` +
  `keyvault.Secret` both created inside `SREDataComponent`, with the
  resulting `Output[str]` password threaded into other components' props
  (e.g. `admin_password=data.password_workspace_admin` in
  `declarative_sre.py`).
- **Local** (used today by Gitea): each component creates its own
  `RandomPassword` and never touches Key Vault, because
  `SREDataComponent` doesn't expose its `key_vault` (`keyvault.Vault`)
  resource — only `key_vault.name` via `exports`.

Recommendation: **centralize**, to match the dominant pattern (6 of 6
existing secrets) and keep all `keyvault.Secret` creation in one place for
future maintainers to find. Concretely:

- Move the `RandomPassword` generation for the workspace-user and
  mirror-user passwords out of `gitea_server.py`/`gitea_mirror_manager.py`
  and into `SREDataComponent`, alongside the existing 6.
- Add two new `RandomPassword` resources there for the admin passwords
  (see §3.2 for why these need a script change too).
- Add four `keyvault.Secret` resources following the exact naming/`opts`
  convention shown in §1.
- Expose all four as `Output[str]` component attributes
  (`self.password_gitea_server_admin`, etc.) the same way
  `self.password_workspace_admin` is exposed today (`data.py:800-818`),
  and pass them into `SREGiteaServerProps`/`SREGiteaMirrorManagerProps`
  from `declarative_sre.py` (same wiring style as
  `admin_password=data.password_workspace_admin`).
- Export the four secret *names* in `SREDataComponent.exports` (not the
  values), matching `password_user_database_admin_secret` etc., so they
  are discoverable the same way as the existing recoverable secrets and
  so a future CLI/provisioning step can look them up via
  `AzureSdk.get_keyvault_secret` if needed.

Alternative considered and rejected for now: leave password generation
local to each Gitea component and instead expose `key_vault` itself from
`SREDataComponent` so `gitea_server.py`/`gitea_mirror_manager.py` create
their own `keyvault.Secret` children. This avoids threading passwords
through more props, but scatters Key Vault secret creation across two
extra files and breaks from the established single-source-of-truth
pattern in `data.py`. Flag as an open question in the PR in case the
maintainers prefer it (e.g. if they'd rather keep Gitea-specific
concerns out of `SREDataComponent`).

### 3.2 Capturing the admin passwords

Gitea's `--random-password` flag never surfaces the password to Pulumi,
so it cannot be wrapped in a `RandomPassword` resource as-is. Both
`configure.mustache.sh` variants (`gitea/gitea` and `gitea/gitea-mirror`)
need to switch the admin user to the same pattern already used for the
workspace user (`configure.mustache.sh:12-21`):

```bash
# Before (gitea/gitea configure.mustache.sh:6)
su-exec "$USER" /usr/local/bin/gitea admin user create --admin \
    --username "{{admin_username}}" --random-password \
    --random-password-length 20 --email "{{admin_email}}" 2> /dev/null

# After
su-exec "$USER" /usr/local/bin/gitea admin user create --admin \
    --username "{{admin_username}}" --password "$ADMIN_SERVER_PASSWORD" \
    --must-change-password=false --email "{{admin_email}}" 2> /dev/null
```

And, mirroring lines 20-21's `change-password` step for the workspace
user (needed for idempotency — the `until ... | grep` loop means this
block may run again against an already-created user on a later
reconcile, and only that step actually forces the password to match the
current Pulumi-generated value):

```bash
su-exec "$USER" /usr/local/bin/gitea admin user change-password \
    --username "{{admin_username}}" --password "$ADMIN_SERVER_PASSWORD" \
    --must-change-password=false
```

Apply the same change to the `gitea/gitea-mirror` configure script for its
own `dshadmin` user. Then add `ADMIN_SERVER_PASSWORD` as a new secure
environment variable on each `gitea` container
(`containerinstance.EnvironmentVariableArgs(name="ADMIN_SERVER_PASSWORD",
secure_value=...)`), the same way `WORKSPACE_SERVER_PASSWORD` is wired in
today (`gitea_server.py:285-288`).

### 3.3 Minor fix while touching this code

`gitea_mirror_manager.py`'s `mirror_password` is exposed as a plain
`Output[str]` (`mirror_password: Output[str] = gitea_mirror_user_password.result`,
`gitea_mirror_manager.py:112`) rather than `Output.secret(...)`, unlike
`gitea_server.py`'s equivalent `workspace_password`. Since this password
is being moved into `SREDataComponent` anyway, wrap it in `Output.secret`
there for consistency with `data.py`'s other password attributes and with
`workspace_password`.

- `docs/source/deployment/deploy_sre.md`: if it documents how to look up
  any of the existing recoverable secrets (e.g. database admin
  passwords), add the four new secret names there for consistency.
- Check for any doc that tells an SRE/researcher how to log into Gitea as
  an admin today (e.g. via a support runbook) — if one exists and

  at the new Key Vault secret.

## 5. Testing

Following the existing conventions in `tests/infrastructure/programs/sre/`
(`pulumi.runtime.Mocks` via `conftest.py`, `@pulumi.runtime.test`,
`resource_assertions.py` helpers):

- **`tests/infrastructure/programs/sre/test_data.py`** (or wherever
  `SREDataComponent` is currently tested — confirm at implementation
  time): assert a `keyvault.Secret` exists for each of the four new
  `secret_name` values (`password-gitea-server-admin`,
  `password-gitea-workspace-user`, `password-gitea-mirror-server-admin`,
  `password-gitea-mirror-user`), each associated with the SRE's Key
  Vault (`vault_name == key_vault.name`).
- Assert the four new attributes on `SREDataComponent` are present and
  are (mocked) `Output[str]` values, and that `exports` contains the four
  new `..._secret` name entries.
- **`SREGiteaServerComponent`**/**`SREGiteaMirrorManagerComponent`**
  tests: assert the `gitea` container's environment variables include a
  secure `ADMIN_SERVER_PASSWORD` entry (in addition to the existing
  `WORKSPACE_SERVER_PASSWORD`/`MIRROR_SERVER_PASSWORD` checks, if/when
  those tests are added — no Gitea component tests currently exist per
  `tests/infrastructure/programs/sre/`, matching the note in
  `specs/configure-mirror-interval.md` §6).
- Out of scope for unit tests (flag as risk instead): whether Gitea's
  `admin user create --password ...`/`change-password` flags behave
  correctly against a running container, and whether the updated
  `configure.mustache.sh` script is still idempotent across container
  restarts — both require a manual post-deploy check.

## 6. Risks / open questions

- **Existing deployed SREs**: an existing Gitea admin user was created
  with Gitea's own random password. After this change deploys,
  `configure.mustache.sh`'s `until ... | grep "{{admin_username}}"` guard
  will find the user already exists and skip the `create` step — but the
  password will *not* be retroactively reset to the new
  `ADMIN_SERVER_PASSWORD` unless the `change-password` step (§3.2) runs
  unconditionally on every reconcile (which the plan above does, mirroring
  the workspace-user pattern). Confirm this is the desired behaviour:
  every existing Gitea admin password will be silently overwritten with
  the newly-generated Key Vault value on next redeploy/restart. This
  seems correct (it's better than an unrecoverable password), but is a
  user-visible change worth calling out explicitly in the PR description.
- **Access scope**: the four new secrets inherit the same Key Vault access
  policy as the six existing ones — full rights for the SHM admin AAD
  group, read-only for the key-vault-reader managed identity. Confirm
  this is the intended audience for Gitea admin credentials (as opposed
  to, say, a narrower group) — no narrower scoping mechanism exists in
  the current Key Vault setup, so this would require a larger access-policy
  change if a narrower audience is wanted.
- **CLI convenience**: no generic `dsh` command exists to print a stored
  secret today (the only CLI-facing secret read is the SHM-level Entra
  application secret, handled differently — see
  `data_safe_haven/config/context.py`). SREs would retrieve these via the
  Azure Portal or `az keyvault secret show --vault-name <name>
  --name password-gitea-server-admin`, using the exported secret names.
  Adding a `dsh sre <name> credentials show` convenience command is a
  reasonable follow-up but is out of scope here unless requested.
- **Centralized vs. local secret creation** (§3.1): flagged for review —
  centralizing in `SREDataComponent` matches existing convention but adds
  four more props to `SREGiteaServerProps`/`SREGiteaMirrorManagerProps`
  and couples `SREDataComponent` to Gitea-specific naming. Worth a second
  opinion before implementation.
